## 1. 当前月度排产规则与算法逻辑

### 1.1 核心业务规则

#### 机台关系规则
- **1喂丝机 → 多卷包机**: 一台喂丝机可以对应多台卷包机
- **只计算卷包机产能**: 喂丝机不参与产能计算，仅用于结果映射
- **机台类型**: 严格区分PACKING（卷包机）和FEEDING（喂丝机）

#### 时间约束规则
- **零时间重叠**: 同一卷包机的时间窗口绝对不重叠
- **工作日历**: 基于aps_monthly_work_calendar表的工作日设定
- **班次配置**: 通过aps_shift_config表计算每日可用工作时间
- **维护计划**: 考虑aps_maintenance_plan表的维护时间约束

#### 产能计算规则
- **速度配置优先级**: 具体配置 > 机台通配符(A1×*) > 产品通配符(*×产品) > 完全通配符(*×*)
- **效率率应用**: 实际产能 = 标准速度 × 效率率 × 可用时间
- **产能验证**: 严格验证can_complete标志确保机台能完成生产

### 1.2 算法执行流程（6阶段Pipeline）

#### Phase 1: 数据加载
- 从9个数据表加载所有排产所需数据
- 验证数据完整性和有效性
- 构建内存缓存提高后续处理效率

#### Phase 2: 时间窗口计算
- 基于工作日历计算可用生产日期
- 结合班次配置计算每日工作时间
- 处理维护计划时间约束

#### Phase 3: 产能计算
- 计算所有卷包机对所有产品的产能矩阵
- 应用速度配置和效率率
- 验证产能约束合理性

#### Phase 4: 调度优化
- 智能机台选择算法（极致轮换策略）
- 严格时间不重叠分配
- 支持大批量产品拆分调度

#### Phase 5: 约束验证
- 多层次约束验证确保结果正确性
- 时间重叠检查和覆盖性验证
- 月度模式宽松验证（允许部分成功）

#### Phase 6: 结果保存
- 机台关系映射（卷包机→喂丝机）
- 生成工单号和调度详情
- 保存到aps_monthly_schedule_result表

### 1.3 调度策略

#### 产品优先级排序
1. **产量大的产品优先**（需要更多时间）
2. **可选机台少的产品优先**（约束更强）
3. **生产时间长的产品优先**（安排更困难）

#### 机台选择策略（极致轮换）
- **从未使用机台**: 10000分优先级
- **使用1次机台**: 1000分优先级  
- **使用多次机台**: 100分优先级
- **强制轮换**: 前N个产品（N=机台数）固定轮换模式

#### 重试策略（4层增强）
1. **机台轮换重试**: 强制尝试所有可能机台
2. **约束放松重试**: 放松时间约束寻找更多可能
3. **强制拆分重试**: 中等产品也强制拆分到多台机台
4. **绝望模式重试**: 最大程度放松约束（降低产量要求）

## 3. ❌ 待解决的关键问题

#### 问题1: 大批量产品排产失败（产品覆盖不完整）
**影响**: 5个大批量产品完全失败，违反"必须所有产品排产"要求

**失败产品列表**:
- `利群(软长嘴)`: 22,700箱 - **系统最大批量产品**
- `利群（蓝天）`: 5,100箱
- `利群（新版）`: 7,800箱  
- `利群(软红长嘴)`: 5,400箱
- `利群(长嘴)`: 5,400箱

**根因分析**:
- 单个产品需求时间过长（例如利群软长嘴需要1261小时）
- 单台机台最大可用时间有限（每台约500-600小时/月）
- 现有拆分算法无法有效处理超大批量产品

**技术细节**:
```
利群(软长嘴): 22,700箱 ÷ 18箱/小时 = 1,261小时
单机可用时间: ~500小时/月
需要机台数: 1,261 ÷ 500 ≈ 3台以上
```

#### 问题2: 时间利用不均衡（只用4天而非20天）
**影响**: 违反"应该有20天的工作日"的用户期望

**现状**:
- 时间跨度: 仅2019-07-01至2019-07-04（4天）
- 工作日总数: 20天可用
- 利用率: 20% (4/20天)

**根因分析**:
- 算法倾向于在最早的可用时间集中调度
- 极致轮换策略导致所有机台在前几天就被占满
- 缺乏跨时间段的负载均衡机制
